# ユーザー管理

`/admin/users`はページング一覧、`/admin/users/{userId}/edit`は基本情報、状態、所属、役職、
直属上司、ロールを管理する。emailは読取専用で外部ID属性を更新しない。

V008で追加した`USER_INFORMATION_MANAGER`は`USER_READ`、`USER_UPDATE`、
`USER_STATUS_CHANGE`、ロール参照・付与・剥奪、組織参照・管理の権限をまとめた業務ロールである。
開発・staging用データでは社長と管理本部長へ全社スコープで付与する。このロールを持つ利用者は
一覧、組織図の編集ボタン、モバイルナビゲーションから同じ編集画面へ移動できる。

編集画面は社員コード、表示名、雇用区分、有効期間、状態、所属、役職、直属上司、ロールを
Backend APIから取得して管理する。emailは将来Microsoft Entra IDを正本とするため
`email（変更不可）`として表示し、更新payloadに含めない。所属の削除操作は行を物理削除せず、
終了日を設定して論理的に終了する。状態、所属、ロールの変更は監査対象である。

画面のリンク・入力・ボタンは`/api/me.permissions`で制御する。表示を隠すだけではなく、
すべてのBFF転送先Backend APIが対応する権限コードを再検証する。
さらにBFFは今回使用する`/api/me`、組織図、ユーザー・所属・ロール・マスタ・監査ログAPIに
ついて、許可したHTTPメソッドとUUID形式のパスだけを転送する。`/actuator`など任意の
Backend APIや未許可メソッドは転送しない。

ユーザー本体と所属更新には`version`を送り、409では「他のユーザーによって更新されています。
最新情報を再読込してください。」と表示する。Frontendの入力補助に加え、期間、主所属重複、
自己上司、無効マスタなどの最終検証はBackendを正本とする。

初期表示中はloading、対象なしはempty、権限拒否は403、楽観ロック競合は409、その他は
汎用エラーとして区別する。Frontendで入力や操作を隠しても、直接URLとBFF経由リクエストは
Backend認可で拒否する。
